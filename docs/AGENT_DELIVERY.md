# Agent 并行开发与交付手册

文档用途：独立重写项目的开发与交付规则。
适用项目：XAU-Next；动态任务状态只在 `planning/work-items.json` 维护。
目标：让多个能力足够的 Agent 独立推进工作，并持续交付可运行的完整流程。

## 1. 从哪里开始

执行开发任务时，先读根目录 `REBUILD_SPEC.md` 中的范围和该任务对应验收项。
改模块边界、依赖方向或运行方式时，再读 `docs/ARCHITECTURE.md`。
接任务、并行开发、整合或交接时，读本手册与 `planning/work-items.json`。
实现请求、响应、事件或分析回答格式时，读 `contracts/` 中对应的权威契约。
实现金额、时间、触发、复盘规则时，读主规格与 `fixtures/acceptance-cases.json` 中对应案例。
读取与当前任务有关的领域代码和接口即可；用到另一个模块时先查其公开接口。

本手册定义开发协作规则，不重复定义产品业务规则。
主规格决定“软件应该做什么”，架构文档决定“职责如何安排”，契约决定“模块如何交换数据”。
任务图决定“这次谁改哪些文件、依赖什么、如何证明完成”。
上述材料冲突时，由集成负责人先统一源文件，再让受影响任务继续。

## 2. 能力驱动的协作

角色表达职责，不绑定模型品牌、型号或厂商。
用户提到的未来模型视为能力愿景；是否可用、具体接口和成本在使用时核实。
选择 Agent 时看它完成当前任务的能力、工具权限、上下文需求和实际验证结果。
模型能力提高后，可以扩大单个任务的闭环范围，并减少不必要的协调步骤。
任务完成标准、产品语义和对外契约继续保持稳定。
增加 Agent 数量需要确实存在独立任务；共享文件争用时先缩小并行范围。

| 角色 | 核心职责 | 可观察的交付 |
|---|---|---|
| 集成负责人 | 分解任务、维护公共契约、分配所有权、整合、验收 | 可运行版本、明确状态、整合证据 |
| 后端领域 Agent | 一个领域的规则、持久化适配与接口实现 | 可调用接口、领域测试、错误行为 |
| 前端 Agent | 页面流程、状态呈现、可访问性与交互 | 可操作页面、契约 mock、交互验收 |
| 数据与运行 Agent | 数据库迁移、运行环境、MT5 bridge、打包 | 可重现启动与恢复、真实只读接入 |
| 审阅 Agent | 检查指定变更的业务正确性与边界 | 有具体触发条件的发现或审阅结论 |

一个 Agent 可以承担多个角色；一个具体文件同时只有一个写入负责人。
集成负责人可以按已授权范围自主拆分、整合、修复和验证。
日常实现细节、可逆本地修改与测试不需要逐项向用户申请批准。
需求发生实质变化，或准备执行未授权的对外动作时，再向用户说明具体选择。
审阅结论是整合证据的一部分；最终验收由集成负责人对当前版本执行。

## 3. 开发协作与产品 AI

开发 Agent 负责构建项目，运行时 AI 负责提供分析内容；二者使用不同职责和状态。
开发任务图不会成为用户每天使用软件时必须操作的功能。
运行时 AI 首版采用人工导出分析包、人工导入回答，经过结构验证后进入业务流程。
以后接入模型 API 时，复用相同的输入、回答 schema、版本和验收样例。
模型选择只影响适配器、提示模板和评估结果，不改金额计算、时间规则或数据库事实。
金额、触发、可用时间与复盘计算由确定性代码执行。

未来模型适配时检查三个能力：结构化输出、所需输入规模、实际响应质量。
适配器返回可验证结果和明确错误，记录模型标识及提示版本。
依据当前可用 API 增加适配器，不提前写一套假想的所有厂商统一框架。
需要研究多个模型时，离线运行同一组案例并比较结果。
运行时多 Agent 分析只有在可测量地改善质量或时延时再纳入产品范围。
开发阶段无需先安装一个万能 Agent 编排框架才能开始。

## 4. 契约先行

权威接口为 `contracts/openapi.json`，采用 OpenAPI 3.1。
分析回答权威格式为 `contracts/analysis-answer.schema.json`，采用 JSON Schema 2020-12。
OpenAPI 通过外部引用复用分析回答 schema，避免手写两份相同结构。
Python wire DTO 与 TypeScript SDK 从契约生成，并保留可重复生成的命令。
FastAPI 导出的规范用于派生校验和语义比对，不能反向覆盖权威契约。
Python 领域对象服务业务计算；wire DTO 服务传输，二者可以使用显式映射。
前端引用生成 SDK；不在页面中另写一套请求或响应类型。

集成负责人是契约、wire DTO 生成流程与 SDK 生成流程的唯一写入负责人。
其它 Agent 发现缺字段、含义不清或状态不足时，提交具体契约变更提议。
提议包含触发场景、拟改字段、示例输入输出和受影响调用方。
集成负责人核对业务语义，更新契约、样例、生成代码并通知消费者。
消费者以新的契约版本继续实现；任务记录中写明当前依据的版本或提交。
无破坏的扩展也需要同步生成物和验收案例，避免前后端理解不同。

mock 由契约及验收样例驱动，至少覆盖成功、空数据、处理中和明确错误。
前端可以在后端未完成时开始交互开发；后端用相同样例验证响应。
mock 的数据来源必须清晰显示在开发环境中。
进入联调后替换数据适配器即可，页面不能依赖 mock 专属字段。
SSE 的事件类型、标识、负载和恢复语义同样放入公开契约。

## 5. 文件所有权

任务的 `owned_paths` 是该任务允许写入的路径。
`inputs` 中列出的材料和依赖模块默认只读。
未分配的文件先由集成负责人明确归属，再修改。
任务遇到所有权外的缺陷时，返回最小复现和修复建议；由负责人修复或移交所有权。
任务切换后可以转移所有权，转移发生前停止旧任务对同一路径的写入。

| 路径 | 唯一维护角色 | 其它任务的协作方式 |
|---|---|---|
| `REBUILD_SPEC.md`、`docs/ARCHITECTURE.md` | 集成负责人 | 提出具体规则或边界变更 |
| `contracts/**`、`fixtures/acceptance-cases.json` | 集成负责人 | 提交契约和案例 diff 建议 |
| 根依赖声明、锁文件、CI 与工作区配置 | 集成负责人 | 提交依赖需求与理由 |
| `packages/api-client/**`、Python wire DTO 生成目录 | 集成负责人 | 修改源契约后统一生成 |
| 后端应用组合入口、路由注册与迁移注册表 | 集成负责人 | 领域任务提交接线清单 |
| 前端应用壳、路由注册与共享样式入口 | 前端壳负责人 | 功能任务提交页面导出与接线清单 |
| 数据库基础设施、迁移文件及迁移测试 | 数据负责人 | 领域任务提交表结构需求 |
| 各领域目录和对应局部测试 | 当前领域任务负责人 | 调用公开接口或提出变更请求 |
| `planning/work-items.json` | 集成负责人 | 返回进度、阻塞和完成证据 |

共享文件角色可以由集成负责人兼任，不要求每个角色配置一个 Agent。
所有权边界是实际路径，不使用“负责后端”“负责体验”这样的模糊授权。
一个任务可以读多个模块，但通过公开服务或接口协作，避免跨领域直接改表。
生成文件由生成流程更新；修改源定义后检查生成结果，不手工修补生成文件。

## 6. 任务粒度和工作环境

每个任务应有一个可演示结果、一组明确文件和一组可运行验收。
任务以“导入一个回答并保存新版本”为粒度，比“写若干类”更容易验证。
过大的任务按独立用户行为拆分；没有独立验收的细碎任务由同一 Agent 连续完成。
两个任务经常互相等待或反复修改同一文件时，合并任务或调整模块边界。

并行写代码时优先使用独立 worktree；每个 worktree 独立安装或使用隔离依赖环境。
每个 worktree 使用独立数据库、附件目录、测试数据根、日志和临时目录。
API 端口、前端端口及 bridge 通道由启动工具分配或显式配置。
启动前检查占用，发现冲突立即报告实际端口并选择空闲端口。
worker 只停止自己启动并记录的进程，避免影响其它任务。
测试使用自己的临时目录；需要固定样例时只读加载 `fixtures/`。

MT5 真实只读接入验证由一个任务独占执行，其他任务使用 bridge fixture。
每个工作区记录代码提交、契约版本、端口、DATA_ROOT 和进程标识。
这些临时运行信息保存在该工作区忽略的状态文件中，不能混入正式配置。
没有可用真实终端时，相关验收保持待验证；其他本地集成继续推进。
单工作树串行开发仍可使用本手册，集成负责人按任务顺序切换所有权即可。

## 7. 任务图

机器可读任务清单位于 `planning/work-items.json`。
下面表格提供人工导航；实际依赖和文件范围以 JSON 为准。
相同一层的任务只有在依赖完成、路径互不冲突且有可用 Agent 时才并行。
后端和前端通过稳定契约对接，前端无需等待全部真实接口完成。

| 任务 | 交付目标 | 可并行方向 |
|---|---|---|
| T00 | 工作区骨架、运行命令、基本检查 | 先建立共同开发基线 |
| T01 | 契约与生成流程落地 | 后续任务共享同一语义 |
| T02 | SQLite、迁移、事务及附件基础设施 | 与前端壳并行 |
| T03 | 行情领域与只读 bridge 实现 | 与分析、方案领域并行 |
| T04 | 分析包、导入、版本与可用时间 | 与行情、方案领域并行 |
| T05 | 方案生命周期、费用与金额计算 | 与分析领域并行 |
| T06 | 前端壳、路由及公共状态组件 | 与后端基础设施并行 |
| T07 | 分析与更新页面，先接契约 mock | 与后端领域并行 |
| T08 | 第一条本地完整流程联调 | 尽早发现契约和持久化问题 |
| T09 | 持仓及成交事实关联 | 第一条流程之外继续推进 |
| T10 | 方案复盘、实际交易复盘与经验 | 使用冻结的事实快照契约，与其它领域并行 |
| T11 | 设置、实验参数与配置持久化 | 与组合业务并行 |
| T12 | 工作台、方案及持仓交互 | 可先接契约 mock |
| T13 | 历史、复盘与设置页面 | 可先接契约 mock |
| T14 | 真实 MT5 只读集成和来源验证 | 同时只占用一个真实接入任务 |
| T15 | 安装、启动、备份与恢复 | 依赖已经可运行的完整基础流程 |
| T16 | 全部验收和性能测量 | 集成后的当前版本上执行 |
| T17 | 完成交付记录和用户操作验证 | 汇总真实完成层级 |
| T18 | 持久任务、幂等与 SSE 事件 | 与后端领域和前端并行，首条流程需要它 |
| T19 | V1.1 可选 40 美元实验回放 | V1 交付后独立推进，不阻挡日常版 |

T08 是尽早执行的集成节点，不能拖到其它功能全部完成以后。
T08 使用真实本地 API、数据库和文件保存，行情可用明确标记的 fixture。
它证明导出、导入、显示、更新、保存和重启恢复这条实现链路。
T14 再补真实来源的连接证据；T16 检查包含全部首版功能的整合版本。
T08 同时依赖 T12 的最小工作台和方案展示、T11 配置及 T18 任务平台。T09/T10 基于 T01 已固定的内部快照接口并行实现，跨域真实接线在集成节点完成。T15 可在等待真实终端时准备打包，最终真实验收仍由 T16 核对。
T16 验收 AC-01 至 AC-22 及 AC-24；AC-23 属于 T19。任务编号是稳定标识，实际执行顺序按 JSON 依赖图，不按数字递增强行串行。
首版交付同时需要真实只读数据、导入更新、金额计算、历史复盘和恢复能力。
漂亮页面、通过 schema 的假数据或单个模块测试，只能证明各自完成层级。

## 8. 派发任务

集成负责人先读取依赖任务结果，再派发下一个可执行任务。
派发包只包含目标、必要输入、契约版本、文件所有权和完成条件。
既有规格通过准确路径和章节引用，不复制全部历史对话。
包含真实数据或外部系统的任务，单独说明数据来源与当前授权边界。

复制下面模板并替换花括号即可：

```text
你负责任务 {task_id}：{title}。
这是 XAU-Next 重写，依据 REBUILD_SPEC.md，不参考旧项目代码实现。
你不是唯一在代码库工作的 Agent；保留他人修改，并兼容当前基线。

工作区：{worktree_path}
可写路径：{owned_paths}
只读输入：{input_paths_and_sections}
契约版本：{contract_revision}
依赖交付：{dependency_results}
验收项：{acceptance_ids_and_cases}

请完成一个可运行结果，包括实现、必要验证和简洁交接。
共享契约、锁文件和组合入口由集成负责人维护；需要变更时给出具体 diff 建议。
遇到缺陷先定位复现条件；能在授权路径内修复的直接修复。
返回修改路径、行为变化、已执行验证及结果、剩余缺口、接线事项。
只有完成条件逐项有证据时才报告 ready_for_integration。
```

启动整个实现阶段时使用：

```text
请依据 XAU-Next 的 REBUILD_SPEC.md、docs/ARCHITECTURE.md、
docs/AGENT_DELIVERY.md 和 planning/work-items.json 开始首版实现。

你担任集成负责人。先核对规格和契约一致性，再执行可用任务。
使用独立 worktree 并行开发互不冲突的模块，按能力选择 Agent。
优先完成 T08 的可运行完整流程，并持续整合后续业务。
自主处理范围内的实现、依赖协调、联调和修复，不逐项请求我确认。
共享契约和组合入口由你统一维护；保留原始记录与他人工作。
交付以真实只读数据、分析更新、预算计算、历史复盘、重启恢复为准。
按主规格执行验收，区分 mock、测试、真实运行和实际交易结果。
首版保持人工交易；记录无法取得的真实验证条件，不虚报完成。
最后提供一键启动方式、验收结果、已知限制和实际文件位置。
```

## 9. 开发循环与整合

任务开始时先构造一条最小可执行案例，确定它如何失败或如何尚未实现。
随后实现最短业务路径，运行针对性检查，再覆盖会改变结论的边界条件。
普通文案和样式调整按视觉与交互验收，避免添加机械镜像测试。
涉及金额、版本、重复导入或恢复的修改必须通过对应业务案例。

worker 完成后提交明确的变更列表和验证证据。
集成负责人检查契约、路径范围、依赖和实际结果，再合入整合分支。
冲突由当前路径负责人或集成负责人解决，依据最终业务语义保留正确内容。
合入后执行受影响的集成验收；工作分支通过不等于整合版本通过。
跨两个模块的缺陷由集成负责人确定事实和边界，分配一个主修复负责人。
每次整合尽量小，避免多个长期分支最后一次性合并。

共享依赖变更使用以下最小请求：
`依赖名称 / 用途 / 建议版本 / 影响工作区 / 替代方案 / 所需新增能力`。
集成负责人先确认现有依赖能否满足，再统一修改声明与锁文件。
批准合入后的锁文件作为下一个基线广播，各任务重新同步依赖并验证受影响部分。
数据库变更同样由数据负责人统一分配迁移编号和执行顺序。
避免多个 Agent 同时生成迁移、改锁文件或注册相同路由。

## 10. 验证与真正完成

任务的 `done_when` 必须每条有可观察证据。
`acceptance_ids` 映射到主规格的验收项，任务创建或范围调整时保持同步。
未映射的验收项属于任务规划缺口，由集成负责人在实现前补齐。
证据至少写明命令或操作、代码版本、输入、预期、实际结果及必要输出位置。
敏感账户或环境值只保存在适当本地材料中，交付摘要使用脱敏标识。

| 验证层 | 完成含义 |
|---|---|
| 静态检查 | 当前代码通过格式、类型、导入边界和生成物一致性检查 |
| 业务测试 | 当前规则在指定案例下得出正确结果 |
| 契约测试 | 真实接口、SDK 与权威契约语义一致 |
| 集成测试 | 当前 API、数据库、后台任务和前端能协作完成流程 |
| 真实接入 | 当前终端的只读数据能够读取、标识和展示 |
| 用户验收 | 用户按启动说明完成日常操作，结果与规格一致 |

需要可重复验证的核心场景包括：重复导入、过期版本、时间边界、费用缺失、
最小手数、持仓重叠、复盘信息可用性、重启恢复及数据源中断后的明确状态。
这些场景的业务期望写在主规格和 fixture，测试引用相同验收标识。
性能测量分别记录本地交互、接口执行、MT5 读取和外部 AI 等待。
性能未达标时按实际慢点优化，不能通过改指标口径宣告通过。
测试通过后只有新变更、新失败或明确疑点才触发扩大或重复验证。

`ready_for_integration` 表示 worker 完成局部交付，尚需整合验证。
`done` 表示任务完成条件全部满足且已在目标整合版本上核验。
T17 完成不自动代表实盘策略盈利、自动交易可用或旧系统已被正式替换。
实现任务只有在对应证据实际产生后才能登记完成或测试通过。

## 11. 失败、恢复与交接

遇到失败先保存原始错误、复现输入和当前版本，再缩小问题范围。
同一失败反复出现时检查原先假设、环境和契约，避免追加无依据补丁。
能独立继续的任务照常推进，受阻任务说明缺少的具体条件。
任务真正需要用户选择时，给出已准备好的选项和影响，不把调查工作留给用户。

暂停、换模型或跨上下文交接时，提交以下最小内容：
`任务 ID / 当前提交 / 目标 / 可写路径 / 契约版本 / 已完成 / 验证 /
原始失败 / 运行环境与 DATA_ROOT / 待完成 / 下一条动作`。
附上必要文件路径和复现命令，避免要求接手者翻阅整段聊天。
接手者先核对工作区和变更，再继续未完成项；新模型无需重新探索全部仓库。
交接信息随该任务保存；长期规则只在权威文档中更新一次。

回滚使用可恢复的提交或精确路径变更，不清空共享目录和工作树。
任务产生的临时文件、进程和端口由该任务在完成时处理。
有验收价值的结果、复现数据和交接材料按项目规则保存。
交付说明聚焦用户能使用什么、如何启动、验证到了哪一层和剩余缺口。
